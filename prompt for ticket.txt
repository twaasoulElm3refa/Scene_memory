# PHASE 2 — CONVERT SUPPORT REQUESTS INTO CONVERSATIONS

The support system must support persistent conversations.

Each support request should become a support conversation, also called a support ticket.

Each ticket contains:

- Unique ticket ID.
- Ticket subject/title.
- User identity.
- Original support message.
- Conversation messages.
- Current ticket status.
- Creation timestamp.
- Last activity timestamp.
- Read/unread state.
- Assigned administrator when applicable.

The ticket must persist in the database.

Users must be able to return to the support page and continue existing conversations.

Administrators must be able to view and respond to the same conversations.

**Both parties must exchange messages inside the same ticket.**

Do not create a new ticket every time a user sends a reply.

# PHASE 4 — IMPLEMENT REAL TWO-WAY MESSAGING

The system must support:

USER → ADMIN

ADMIN → USER

### User behavior

The user can:

- Create a support ticket.
- View all authorized conversations.
- Open a conversation.
- Read administrator replies.
- Send additional messages.
- See message timestamps.
- See whether a ticket is open, pending, or resolved.
- Identify unread administrator replies.

### Administrator behavior

The administrator can:

- View incoming support tickets.
- Open any ticket they are authorized to manage.
- Read the complete conversation.
- Reply directly to the user.
- View the user's response.
- Manage ticket statuses.
- See unread user messages.
- Track latest ticket activity.

### Example conversation

```text
Ticket: مشكلة في شراء خطة

USER:
السلام عليكم، عندي مشكلة في الدفع باستخدام PayPal.

ADMIN:
وعليكم السلام، ممكن توضح الخطأ اللي بيظهر؟

USER:
بيظهر إشعار إن العملية فشلت.

ADMIN:
تمام، هنراجع المشكلة ونتابع معاك.
```

Every message must be saved in the database.

Messages must remain available after refreshing the page or logging in again.

Use the same conversation identifier throughout the entire conversation.

Inspect the existing database first.

Reuse existing support tables whenever possible.

Recommended logical design:

## Support Tickets

```text

subject

last_message_at

```

Use the existing messages table if suitable, or create `support_messages`.

Suggested fields:

```text

sender_type

created_at
updated_at
```

Sender types must be validated and assigned server-side, not trusted from client input.

If needed, implement separate participant-specific read tracking to correctly support unread counts for multiple administrators.

### Important database requirements

- Use foreign keys.
- Use appropriate indexes.
- Preserve historical support requests.
- Never delete existing support data.
- Never create duplicate tickets on submission retries.
- Preserve sender identity.
- Support multiple messages per ticket.
- Store timestamps consistently.
- Keep messages ordered by reliable timestamp and ID.
- Use appropriate MySQL constraints.
- Design for pagination.
- Avoid unnecessary migrations.

If existing support records represent only single messages, plan a safe backward-compatible conversion or migration.

Do not silently destroy or orphan historical messages.

**Database structure is flexible, but persistence and conversation integrity are mandatory.**

# PHASE 7 — AUTHENTICATION AND SECURITY

Use Laravel's existing authentication, Sanctum, permissions, and role system.

### Authenticated users

Authenticated users may access only their own support tickets.

Never allow a user to retrieve another person's conversation by changing a numeric ticket ID.

Enforce ticket ownership server-side for:

- Listing.
- Reading.
- Sending replies.
- Updating relevant user-controlled fields.

### Guest users

Inspect whether the current contact form supports guests.

If guest submissions are currently supported, preserve that capability.

For guest conversations, implement a secure access mechanism using a time-limited or revocable signed access link and appropriate verification.

Do not allow guest access simply because someone knows an email address or ticket ID.

Do not silently force login if existing support functionality allows anonymous contact.

### Admin authorization

Only administrators with the appropriate existing permissions can:

- List all tickets.
- View other users' conversations.
- Reply as support staff.
- Update ticket status.
- Assign tickets.

Do not allow users to impersonate administrators.

### Input safety

- Validate message lengths.
- Escape user-generated content.
- Prevent XSS.
- Prevent mass assignment.
- Respect CSRF/Sanctum requirements.
- Rate-limit ticket creation and message sending.
- Protect sensitive contact information.
- Avoid leaking ticket contents in errors or logs.

# PHASE 8 — MESSAGE UPDATES AND NOTIFICATIONS

The conversation must feel interactive.

If the project already uses Laravel broadcasting, WebSockets, or a compatible real-time mechanism, reuse it.

Otherwise, implement lightweight and efficient polling for active conversations.

Suggested behavior:

- Check for new messages approximately every 10–15 seconds while the conversation is open.
- Stop polling when the relevant component is unmounted.
- Avoid polling hidden or inactive conversations unnecessarily.
- Prevent overlapping requests.
- Use pagination or incremental message fetching.
- Update unread counts appropriately.
- Refresh the conversation after sending a message.

Do not introduce an unnecessary Redis/WebSocket infrastructure dependency solely for support chat.

### Notifications

Use the existing notification/email system where suitable.

When a user creates a ticket:

- Notify the appropriate support team.

When a user sends another message:

- Notify support staff as appropriate.

When an admin replies:

- Notify the user.
- Mark the conversation as having an unread admin message.

Notifications must not create duplicate tickets.

A mail transport failure must not destroy or roll back a successfully stored message unless existing explicit business rules require it.

Prefer after-commit queued notifications with proper failure handling.
