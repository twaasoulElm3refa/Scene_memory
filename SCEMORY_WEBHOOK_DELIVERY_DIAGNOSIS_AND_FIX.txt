SCEMORY WEBHOOK DELIVERY DIAGNOSIS AND FIX
Date: 2026-07-19
Branch: fix/scemory-webhook-delivery

1. Executive Summary
The Laravel webhook routes are present as POST endpoints under /api/v1 and are not protected by auth:sanctum. I implemented the practical fix found in the repository: the purchase webhook config now accepts PAYPAL_WEBHOOK_ID, which is the variable named in the deployment instructions, while preserving the older PAYPAL_CHECKOUT_WEBHOOK_ID fallback.

I also added safe endpoint and processing logs, plus a diagnostic command:
php artisan payments:diagnose-webhooks

Local internal curls prove that both endpoints reach Laravel and return JSON 400 without PayPal signature, which is the expected fail-closed behavior.

2. Exact Root Cause
Confirmed code-level root cause for purchase webhooks:
config/paypal.php was reading only PAYPAL_CHECKOUT_WEBHOOK_ID for the purchase webhook. The requested/deployment variable is PAYPAL_WEBHOOK_ID. If the CWP/Hostinger environment contains PAYPAL_WEBHOOK_ID but not PAYPAL_CHECKOUT_WEBHOOK_ID, the endpoint reaches Laravel but fails with webhook_id_not_configured and returns HTTP 503 before signature verification.

Fix applied:
config('paypal.webhook_id') now reads PAYPAL_WEBHOOK_ID first and falls back to PAYPAL_CHECKOUT_WEBHOOK_ID.

Wallet webhook was already reading PAYPAL_WALLET_WEBHOOK_ID.

PAYPAL-TRANSMISSION-TIME
PAYPAL-CERT-URL

It validates PayPal cert URL host against sandbox/live mode and calls PayPal verify-webhook-signature using the route-specific webhook ID.
