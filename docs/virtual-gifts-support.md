# Scemory virtual gifts and support

## Implemented feature

Authenticated users can support an event owner or an individual comment author from the event details page. Both actions use `VirtualGiftModal.vue`, the existing authentication/API clients, and the same server-side purchase workflow. `/LANG/gifts` provides sent/received histories, payment verification, creator balances, and withdrawal requests. `/admin/gifts` adds catalog editing, translations, secure image uploads, transaction filters, audit access, financial reports, refunds, reconciliation, and withdrawal approval/recording within the existing admin layout.

All new interface text supports the existing 13 languages, including Arabic RTL. Bundled gift artwork is original, code-authored SVG; uploaded images are restricted to JPEG, PNG, or WebP, at most 2 MB and 4096 × 4096 pixels. Uploaded filenames are generated by Laravel. Replacing an image retains previous files because transaction snapshots may still reference them. Delivery feedback uses a lightweight animation disabled by reduced-motion preferences.

The catalog seeder supplies Coffee Cup ($1), Cake Slice ($3), Rose ($5), Gift Box ($10), and Golden Trophy ($25), with localized names and images. `VirtualGiftSeeder` uses `firstOrCreate` by stable slug: rerunning it never overwrites administrator edits, deactivation, images, prices, or translations. Prices come from database records, never frontend constants or a payment-service price list. Catalog deletion deactivates a gift; financial history remains intact.

Gifting does not call `PointService`, change `point_rules`, or award lifetime/weekly points. The Saturday–Friday competition implementation is unchanged.

## Database and ledger architecture

The additive migration is `database/migrations/2026_10_18_000001_create_virtual_gift_tables.php`:

| Table | Purpose |
| --- | --- |
| `virtual_gifts` | Administrator-controlled catalog, prices in minor units, translations, images, order, availability |
| `gift_transactions` | Immutable gift/price/quantity/currency/15% commission snapshots, existing payment linkage, provider IDs, delivery/settlement status, fee evidence and precision, refunds and review flags |
| `gift_earning_entries` | One recipient entitlement per transaction, with separate pending, available, reserved, settled, reversed, and recovery projections |
| `gift_transaction_events` | Append-only audit events with unique event keys and safe metadata |
| `gift_earning_movements` | Append-only signed changes to financial buckets; unique operation keys prevent repeat release/reversal/settlement |
| `gift_withdrawals` | Dedicated creator payout requests, approval status, encrypted destination details, and unique external payout references |
| `gift_withdrawal_allocations` | Exact reservation of specific earning entries for each payout request |

Gift references, payment IDs, sender-scoped idempotency hashes, provider order/capture IDs, wallet debit references, earning transaction IDs, and movement keys have uniqueness constraints. Financial relationships within these tables use restrictive foreign keys. Gift payments cannot be deleted through legacy payment/purchase/user cascades; account-data removal must retain or anonymize financial records rather than delete these references. Historical event/comment/recipient identifiers are retained without cascading deletion.

The earning invariant is enforced on every movement:

```text
pending + available + reserved + settled + reversed = original recipient share
```

Recovery is a separate receivable for money already paid externally before a refund. It is not counted a second time as an entitlement. Projections and their audit movements update in the same database transaction; neither the application nor the migration deletes financial entries.

The existing `purchases` and `payments` tables carry the new `virtual_gift` purpose. No existing wallet, payment, history, ranking, or commission records are backfilled or replaced. Existing wallet debits use `WalletLedgerService::post` and a unique gift debit key. A wallet-funded refund posts a compensating credit with its own unique key, retaining the original debit.

## Money and fixed commission

All authoritative calculations use integers. For the complete transaction, including quantity:

```text
gross_minor = unit_price_minor × quantity
commission_minor = intdiv(gross_minor × 15 + 50, 100)
recipient_minor = gross_minor - commission_minor
```

This is deterministic half-up rounding once on the final gross amount. For example, a 10-cent transaction allocates 2 cents to Scemory and 8 cents to the recipient; ten 1-cent gifts in one transaction use the same final-total calculation, rather than rounding each unit separately. Neither users nor catalog administrators can override the 15% rule or historical financial snapshots.

The existing wallet and `MinorMoney` use two decimal places. Gift currencies are initially USD, EUR, GBP, EGP, SAR, and AED; wallet checkout requires the actual wallet currency to match. No FX is invented. Direct PayPal checkout rejects gift currencies outside PayPal's supported two-decimal list; catalog responses expose permitted payment methods. Currency support in a merchant account must also be configured at PayPal. [PayPal currency reference](https://developer.paypal.com/api/codes/currency/).

Quantity is 1–100. Total purchase value is capped at 99,999,999 minor units to fit the existing `purchases.amount` DECIMAL(8,2) column. The modal echoes its displayed unit price/currency as optional expected values; the backend rejects changed catalog prices before creating a new purchase. These values never determine the charge. Retries of an already-created transaction retain its original quote. Uncertain wallet attempts preserve their idempotency key and displayed selection in session storage so reopening the modal can verify the same purchase.

## Payment lifecycle and existing PayPal integration

```text
validated target/catalog → pending gift + existing purchase/payment snapshot
    wallet: locked debit → paid → delivered once → pending earning
    PayPal: existing gateway creates order → user approves → server capture verifies
            → paid → delivered once → pending earning
```

The recipient is always derived from the persisted event/comment. The event must be active and not deleted; comments must exist and belong to that event. Sender and recipient must be active when quoting, and self-gifting is rejected. Existing comment deletion rules are retained; deleted comments cannot receive a new gift. Eligibility and price checks are performed on the server. A paid PayPal gift whose recipient becomes unavailable is retained for review rather than silently losing the payment evidence.

Wallet checkout locks the sender, purchase/payment, gift, and wallet as appropriate; insufficient funds or any failed ledger/earning write rolls back the complete operation. A mismatch between the legacy wallet amount and its minor-unit projection fails closed for reconciliation. This does not silently repair or reinterpret existing financial balances.

PayPal integration points:

- `PayPalServices` adds gift order creation, purpose-aware capture/reconciliation, refunds, and verified refund lookup alongside existing purchase handling.
- `PayPalGateway` retains its existing SDK/client factory, credentials, configuration, and OAuth mechanism. Added capture/refund detail methods use that client. The installed SDK's `refundCapturedPayment` helper requires a float, so the new gateway refund method reuses its existing OAuth/configuration and sends an exact decimal string through Laravel HTTP to the same PayPal API. No second PayPal SDK client or credentials were introduced.
- `PaymentFinalizer` dispatches gift finalization to the gift accounting service. Existing media fulfillment and wallet-deposit methods keep their behavior.
- `PaymentFinancialValidator` verifies completed capture status, amount, currency, owning purchase/user, stored order ID, custom/reference IDs, merchant ID, and globally unique capture ID before delivery.
- `PayPalOrderResolver`, `PayPalWebhookProcessor`, and the existing signature verifier route verified gift events through `/api/v1/paypal/webhook`. No old callback URL or credential was replaced. Wallet deposits keep their separate existing webhook/purpose.
- The existing `payments:reconcile` job includes pending gifts and periodically checks completed gift captures for fees and reversals. Admins can also reconcile an individual gift.

Order creation and capture use stable `PayPal-Request-Id` values tied to the gift reference. Browser return/cancel navigation grants nothing. Return URLs preserve the checkout language, then the authenticated client verifies the stored reference. The client cannot supply another order's capture token to select a payment. Provider approval alone does not deliver a gift; a pending capture remains pending. [PayPal order/capture flow and idempotency](https://developer.paypal.com/api/rest/integration/orders-api/api-use-cases/advanced/).

Signature verification remains enabled according to the existing PayPal configuration; no verification bypass was added. Duplicate signed webhooks, requests, callbacks, capture attempts, and earning releases cannot create duplicate debits, delivery, or entitlements. The frontend checks pending status after capture and offers manual verification after bounded polling.

## Provider fee accounting and reports

`seller_receivable_breakdown.paypal_fee` is authoritative capture fee evidence. Confirmed fee amount, currency, and decimal precision are stored separately from the fixed commission. Missing fees remain NULL/unknown, never an assumed zero. Reconciliation can confirm or correct the fee snapshot; audit changes do not become additional expense rows. Wallet-funded gifts have no second provider fee (`not_applicable`, with a null fee amount). [PayPal capture fee data](https://developer.paypal.com/sdk/orders/v2/definitions/capture/).

Fees in JPY, HUF, and TWD retain PayPal's zero-decimal precision. Supported two-decimal fee currencies use the existing integer converter. Unsupported fee denominations are flagged for review. Amounts in different currencies are reported separately; the platform does not subtract a foreign-currency fee from USD commission using an invented rate. [PayPal currency precision](https://developer.paypal.com/reports/reference/supported-currencies?swcfpc=1).

For a $10 gift, the recipient's entitlement is $8.50 and gross commission is $1.50. If actual confirmed processing cost is $0.60, net platform revenue is $0.90. A $1 gift with that actual cost produces negative 45-cent platform revenue while the recipient still earns 85 cents. No fee percentage or flat fee is assumed in production code.

Reports distinguish:

- Original captured gift gross volume, wallet/PayPal volumes, and separately reported refunds.
- Retained gift value after refunds, recognized commission, and recipient entitlement after compensating reversals.
- Known processing costs grouped by fee currency/precision.
- Net platform revenue after recorded same-currency processing costs; it is explicitly provisional/null when fees are unknown or require currency conversion.
- Pending, available, reserved, settled, reversed earnings, and recovery receivables.
- Actual recorded external payout totals by currency/status, separately from current earning entitlements.
- Failed/pending payment counts, gift popularity, supported events, and paginated recipient reports.

Gross gift payments are never presented as platform revenue. A pending earning is never described as an external payout. Original confirmed capture costs remain recorded through refunds unless authoritative provider data changes the cost snapshot; no processing-fee refund is guessed.

## Earnings, withdrawals, refunds, and disputes

`GIFT_HOLDING_DAYS` defaults to **7 development-policy days after verified payment**. It is configurable, must be nonnegative, and is not a claim of provider finality. Each gift stores its own release timestamp. `gifts:release-earnings` runs hourly, releases due eligible earnings to the dedicated creator ledger, and skips disputed/reviewed/inactive accounts. Rerunning it cannot release the same earning twice. User balances expose currently withdrawable funds separately from blocked ledger balances.

The existing withdrawal implementation updates legacy wallet amounts with floats and lacks the integer-ledger reservations needed for these entitlements. It was inspected and left unchanged; creator gifts therefore use a dedicated earnings/withdrawal ledger rather than making spending-wallet credit externally withdrawable. The existing Sanctum/admin authorization and admin layout are reused.

Creator withdrawal lifecycle:

1. An active recipient requests an amount in an available earnings currency and supplies payout destination details.
2. A transaction locks the recipient and reserves specific earning entries. Concurrent/duplicate requests cannot reserve the same money twice. Destination details are encrypted using the application's existing `APP_KEY`.
3. An administrator approves the request. Rejected/cancelled requests append reservation reversals.
4. An administrator records a genuinely completed external payout with a unique external reference. This moves reserved earnings to settled. The application does **not** issue an external PayPal/bank payout or claim one happened automatically.
5. Already-paid payout references and financial history cannot be changed by repeating an update.

Refunds before release compensate pending earnings; refunds after release compensate available earnings. Outstanding withdrawal reservations containing the refunded gift are cancelled atomically. If money has already been paid externally, the settled entitlement is reversed and a recovery receivable is recorded. Further withdrawals in that currency are blocked until an administrator records actual recovery with an external proof reference. Review flags require a separate explicit clearance.

Wallet refunds credit only the original sender's compatible spending wallet, once. Direct PayPal refunds use the original capture through the existing gateway, and reverse the earning only after a completed provider refund is verified. PENDING refunds freeze release for review and await provider confirmation. Full refunds and partial refunds use cumulative half-up commission reversal, preserving the original gross/commission/share snapshots and appending compensation rather than deleting rows.

Verified refund IDs are idempotent across admin actions and webhook retries. If a full refund arrives before its completion webhook, authoritative server capture evidence can record the original captured entitlement and its complete reversal atomically, so no refunded gift becomes visibly delivered. `REFUNDED`/`PARTIALLY_REFUNDED` capture evidence is accepted only in this gift recovery path; ordinary purchase/deposit completion validation remains strict.

Partial capture status alone does not reveal every refund's amount. A changed partial-refund revision freezes the gift even when an earlier refund is already known. Admins reconcile missing refund IDs against PayPal's refund-detail API, which verifies completion, capture ownership, currency, and amount; then clear review with a proof reference after checking completeness. If PayPal omits its capture revision timestamp, the review marker refreshes daily rather than treating an old review as permanent provider finality.

Dispute-created/resolved events freeze funds for review. An outcome code alone does not establish an exact money movement. Verified capture-reversal/refund evidence drives financial compensation. Partial or otherwise unsupported recovery situations remain flagged; administrators must not clear review without confirming provider records. [PayPal refund API](https://developer.paypal.com/api/payments/v2/captures-refund).

## API reference

New routes use the project's `{status,message,data}` response convention. Public catalog/summary routes are throttled; all personal payment/history/earnings routes require Sanctum; admin routes additionally require the existing `AdminMiddleware`. Payment/gateway responses are never dumped into public history. Another user's private reference returns 404.

| Method / path | Behavior |
| --- | --- |
| `GET /api/virtual-gifts` | Active catalog with translations, image URLs, authoritative prices and permitted payment methods |
| `POST /api/gifts/send/wallet` | Atomic wallet gift purchase |
| `POST /api/gifts/paypal/create-order` | Pending gift plus existing PayPal checkout approval URL |
| `POST /api/gifts/paypal/capture` | Sender-owned reference, authoritative server reconciliation/capture |
| `GET /api/gifts/{reference}/status` | Private sender/recipient status and public identity fields only |
| `POST /api/gifts/{reference}/cancel` | Cancel an unpaid gift; never undo a paid capture |
| `GET /api/gifts/paypal/return` | Navigation only; no financial fulfillment |
| `GET /api/events/{event}/gifts/summary` | Owner-support totals for the visible event |
| `GET /api/comments/{comment}/gifts/summary` | Support totals for that visible comment |
| `GET /api/gifts/sent`, `GET /api/gifts/received` | Paginated private histories |
| `GET /api/gifts/earnings` | Creator balances, withdrawable funds, own wallet denomination/balance, holding policy |
| `GET/POST /api/gifts/withdrawals` | List/request creator withdrawals |
| `POST /api/gifts/withdrawals/{reference}/cancel` | Owner cancellation of a pending reservation |
| `GET/POST /api/v1/admin/gifts/catalog` | List/create catalog |
| `POST/DELETE /api/v1/admin/gifts/catalog/{id}` | Update/deactivate; never erase paid gift history |
| `GET /api/v1/admin/gifts/transactions` | Paginated filters: status, payment method, recipient ID, review flag |
| `GET /api/v1/admin/gifts/transactions/{reference}/audit` | Audit events and signed earning movements |
| `POST /api/v1/admin/gifts/transactions/{reference}/actions` | `reconcile`, `refund`, `reconcile_refund`, `recover`, `clear_review` |
| `GET /api/v1/admin/gifts/report` | Currency-separated financial/recipient reports |
| `GET /api/v1/admin/gifts/withdrawals` | Administrator payout queue |
| `POST /api/v1/admin/gifts/withdrawals/{reference}` | Approve/reject/record paid with external reference |

Purchase payload:

```json
{
  "gift_id": 1,
  "event_id": 42,
  "comment_id": null,
  "quantity": 2,
  "idempotency_key": "a-persisted-unique-purchase-key",
  "expected_unit_price_minor": 100,
  "expected_currency": "USD"
}
```

Omit `comment_id` or use null for event-owner support. Expected price/currency are optional stale-quote guards; they do not control pricing. Recipient, final amount, or paid status cannot be supplied as authority. Keep the same idempotency key after a timeout; use a new key only for a genuinely new purchase.

Capture accepts `{ "reference": "gift-uuid" }`. Admin refund actions refund the remaining paid amount rather than accepting a client-priced refund. `reconcile_refund` accepts `proof_reference` containing the PayPal refund ID and verifies it remotely. `recover` accepts integer `amount_minor` plus a real external `proof_reference`; `clear_review` requires a proof reference and rejects unresolved disputes, outstanding recovery, or unconfirmed requested refunds.

User withdrawal requests contain positive integer `amount_minor`, matching `currency`, an idempotency key, and `payment_details: {method,destination}`. Recording paid status requires prior approval and a unique `payout_reference`; this endpoint records a completed external action, it does not perform it.

Public gift summaries exclude fully reversed gifts and keep originally delivered quantities for partial refunds, while monetary summaries subtract refunded amounts. They do not reinterpret fractional money refunds as fractional gift units.

## Deployment and rollback

No application database migration or real financial transaction was executed during development. Normal application/MySQL containers were stopped and no project `.env` existed. Tests used in-memory SQLite or a separate MySQL server with its data directory on tmpfs and no application volume attached. PayPal was mocked or HTTP-faked in Sandbox mode; real Sandbox checkout still requires configured project credentials and merchant/webhook settings.

Existing provider credentials/configuration are reused: `PAYPAL_MODE`, its existing mode credentials, `PAYPAL_MERCHANT_ID`, checkout webhook ID, application/frontend URLs, and the existing signature-verification settings. `APP_KEY` is required for encrypted payout destinations. Do not replace a deployed key without the application's normal key-rotation process.

New environment settings:

```dotenv
VIRTUAL_GIFTS_ENABLED=true
GIFT_HOLDING_DAYS=7
```

Deploy through the existing release process after verifying the intended database and taking its normal backup. Review pending migrations first. On an otherwise current database:

```sh
docker compose exec app php artisan migrate:status
docker compose exec app php artisan migrate --force --path=database/migrations/2026_10_18_000001_create_virtual_gift_tables.php
docker compose exec app php artisan db:seed --class=VirtualGiftSeeder --force
```

Ensure the public storage link exists for uploaded images (`php artisan storage:link` only when absent), build/deploy frontend assets, refresh normal application caches, and restart long-lived workers through the existing deployment process. The host must continue running Laravel's scheduler every minute. Confirm `gifts:release-earnings` appears hourly and `payments:reconcile --limit=100 --age=10` remains every five minutes. Monitor failed reconciliation/webhook events and increase job limits or run targeted admin reconciliation for backlogs.

Configure the existing **checkout** PayPal webhook to include order approval; capture completed/pending/denied/declined/refunded/reversed; and dispute created/resolved events, where supported for the merchant account. Keep existing purchase/deposit subscriptions and URLs. Perform a real Sandbox approval/capture/refund smoke test with a second user and verify merchant/currency amounts before enabling gifts in a live deployment.

For rollback, set `VIRTUAL_GIFTS_ENABLED=false` and refresh the normal configuration cache. This stops new quotes/catalog checkout while retaining existing-order retries, capture/status verification, refunds, admin review, and owed earnings. Roll back UI entry points as needed, but retain payment/webhook/ledger handlers for outstanding gifts and later provider reversals. The migration's `down()` deliberately retains financial tables: do not use a database rollback that discards their migration state, and never truncate gift, wallet, payment, or earning history.

The clean historical MySQL migration chain already has media-table naming inconsistencies (`events_imges` versus `events_images`). Those migrations were not changed. The isolated MySQL test runner creates both empty media table spellings only in its disposable fixture, then applies required legacy user/wallet/payment migrations and the new gift migration with foreign-key checks enabled. This is not a production schema-repair procedure. Existing installations should apply the additive gift migration to their verified current schema.
